# first setup of schemas (in postgres & Drizzle)

Step 1: Create the SQL Initialization Script
  When the Postgres container starts for the very first time, it looks for any .sql files in /docker-entrypoint-initdb.d/. We will use this to create your schemas.
  Create a folder: packa/database/init/
  Create a file: init.sql
    ```
    // init.sql
    CREATE SCHEMA IF NOT EXISTS auth_service;
    CREATE SCHEMA IF NOT EXISTS lobby_service;
    CREATE SCHEMA IF NOT EXISTS game_service;
    ```

  Update your docker-compose.yml to map this file
    ```
    // docker-compose.yml
    postgresql-rdbms:
        image: postgres:17
        volumes:
          - postgresql_data:/var/lib/postgresql/data
          # Add this line to run your schema creation script:
          - ./backend/database/init/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    ```

Step 2: Define the schemas in Drizzle

  1. Structure your packages/database/src/
  Keep each service's schema in its own file.

    =============================================================
    /packages/database/src/
    ├── auth.schema.ts
    ├── lobby.schema.ts
    ├── game.schema.ts
    └── index.ts  <-- This will "collect" them for easy importing
    =============================================================


  2. Configure drizzle.config.ts - This file tells Drizzle where to look for your schema definitions.
    ```
    // packages/database/drizzle.config.ts
    import { defineConfig } from "drizzle-kit";

    export default defineConfig({
      schema: "./src/*.schema.ts", 
      dialect: "postgresql",
      dbCredentials: {
        url: process.env.DATABASE_URL!, 
      },
    });
    ```


  3. The index.ts File (The "Collector")
  This file acts as a shortcut. When you import from @big2/database in your services, you'll want a clean way to get your tables.
    ```
    // packages/database/src/index.ts
    export * from "./auth.schema";
    export * from "./lobby.schema";
    export * from "./game.schema";
    ```

  You do not need import statements in your index.ts because you are using export *.

    Why this works?
    export * is a shorthand that tells TypeScript: "Take everything that is exported from auth.schema.ts and re-export it from this file."
    It acts like a funnel. When your backend services import from @big2/database, they are actually grabbing the exports from your schema files through this index.ts file.

    One important detail!
    This only works if you are using named exports in your schema files, Example auth.schema.ts:
    Because authSchema and users are both exported with the export keyword, the export * from "./auth.schema" in your index.ts will successfully grab both of them.

    ?? When would you need an import ??
    You would only need import in index.ts if you were doing logic inside that file. For example, if you wanted to create a single database connection instance for the whole project to use:
      ```TypeScript
      // If you wanted to do this, then you WOULD need imports:
      import { drizzle } from "drizzle-orm/node-postgres";
      import { Pool } from "pg";
      export const db = drizzle(new Pool({ connectionString: ... }));
      ```
    But for simply "collecting" your schemas, the export * method is the cleanest and most common pattern in TypeScript projects. 
    It keeps your code tidy and prevents your index.ts from becoming cluttered with import lines.

Step 3: Connecting the Microservices
  Now, when you run your auth-service container, you provide the DATABASE_URL with the ?schema=auth_service parameter.
  The "Magic" of this approach:
  Drizzle Kit (when you run migrations) sees all three schemas because it connects to the "Master" URL.
  Auth Service (when it runs) is restricted to auth_schema because of the ?schema parameter.
  Postgres organizes the physical tables internally as auth_schema.users, game_schema.matches, etc.

Step 4: How to verify it works
  Run your stack: docker-compose up
  Push your schema: Run npx drizzle-kit push (or migrate).
  Check the database:
    Open your terminal and enter the database container:
    docker exec -it postgresql-rdbms psql -U admin -d big_two_db
    Type \dn (this lists all schemas).
    You should see: auth_service, lobby_service, game_service, and public.

One Final Tip: The public schema
  Postgres always has a public schema by default. 
  Ignore it. 
  Just leave it empty and put all your work into the three schemas you created in init.sql.

This is the entire pipeline with the sequence of "Initialize SQL" -> "Define in Drizzle" -> "Restrict via Connection String" 


6. Using them in your microservices
Now, in your auth-service (or any other service), you import exactly what you need. Because of the index.ts file, it looks very clean:
```TypeScript
// backend/auth-service/src/index.ts
import { users } from "@big2/database"; 
// Even though you import 'users', Drizzle knows it belongs 
// to 'auth_service' because it's defined in that schema.
```


SECURITY MEASURES - PERMISSIONS

When you run CREATE SCHEMA auth_schema;, 
  Postgres creates that schema. 
  By default, every user has permission to see and use that schema. 
  This is not "private" yet.

To make postgres schemas truly "private" 
  (meaning game_service cannot touch auth_schema), 
  must use Postgres permissions (GRANT/REVOKE).

The "Migration/Owner" User (The Super User):
  Use your POSTGRES_USER_ADMIN (the admin user) when running drizzle-kit migrate or drizzle-kit push. 
  This user has the power to create tables, change schemas, and grant permissions. 
  Drizzle uses this user to manage the structure.

  The "Layered" Loading Strategy
  Docker Compose allows you to specify multiple env_file entries. 
  When you list them, the ones at the bottom override the ones at the top.
  To keep your sanity, never duplicate the same variable in both files. (root/.env & service/.env)

need _FILE in environment docker compose?
  => your application code vs third-party software (like Postgres)
  The Short Answer
    You MUST keep the _FILE suffix for the official Postgres container.
  The Explanation
    There is a fundamental difference in how they work:
      Your Application (The one you write): 
        You control the source code. You are writing the fs.readFileSync logic. 
        You decide how it reads the password.
      The Postgres Container (The one you download): 
        You do not control the source code. 
        It is a pre-compiled image. 
        The people who built the Postgres Docker image wrote their own internal script (the "entrypoint") to look for environment variables ending in _FILE.
        If you don't use POSTGRES_PASSWORD_FILE, the Postgres container won't know to look in /run/secrets/. It will just keep looking for POSTGRES_PASSWORD (the plain text version).
  Think of it like this:
    Postgres is a pre-built appliance. You have to follow the manufacturer's manual (using the _FILE syntax).
    Your Apps are custom-built furniture. You can design them to work exactly how you want (reading the files directly).

The Secret Volume Path
  Your logic is correct, but be careful with Mount Point Collisions.
  If you mount - ../secrets:/run/secrets:ro, you are taking everything in your local secrets/ folder and dumping it into /run/secrets/ inside the container.
  The Pro: It is incredibly short and easy to manage.
  The Con: Your container now has access to every secret in your entire project, even secrets it doesn't need (like potentially your Stripe API keys, AWS credentials, etc.).

The "Init" Problem: Is there a better way?
  The reason I taught you the init.sql method is that it is the standard way to bootstrap a new environment. 
  Every dev who clones your repo needs a database that just works on the first docker compose up.
  The Industry Standard for "Day 2" changes (changes after the DB is built):
  Migrations (The Golden Rule): In a professional environment, you don't manually edit init.sql. You use Migration Tools (like drizzle-kit, flyway, or liquibase).
  How it works: Every time you need a new table or a new permission, you create a new migration file (e.g., 0001_add_chat_table.sql).
  Automation: When your service starts, it runs these migration files automatically. If the migration was already run, the tool skips it.
  The "Makefile Harden" approach: For security hardening (like REVOKE or CREATE USER), which you usually only run once at the very end of your project setup, the make harden command we discussed is perfect.
  Don't feel like you were taught wrong. You were taught the "Bootstrap" phase. The "Maintenance" phase (Migrations) comes next as your project grows.

Are schema names in .env "Industry Standard"?
  No. Using .env for schema names is generally overkill.
  The Industry Standard: Keep schema names hardcoded (e.g., auth_schema) in your SQL and your code. 
  Why? Because your code needs to know the schema name to connect to it. 
  If you change the schema name in your .env, your code will break immediately unless you also change it in your schema.ts. 
  Hardcoding them makes the system more stable.

psql?
  psql is the official, interactive command-line terminal for PostgreSQL. 
  Think of it as a "shell" specifically for your database—just like your terminal is a shell for your operating system. 
  You use it to type in SQL queries, manage database tasks, and check the status of your tables directly from your terminal.  

defaults for Postgres' environments
  POSTGRES_USER: Defaults to postgres.  
  POSTGRES_DB: Defaults to the value of POSTGRES_USER (so, postgres).

variable namings od schema
  The variable authSchema is just an object you use in your code to group tables.
  MINE => The string "auth_schema" is the physical location in the database where Postgres stores the tables.  

Can I make the schema accessible by its own service AND Drizzle?
  Yes, easily. In fact, Drizzle is the tool that your service uses. When you perform a migration, Drizzle acts as the "Owner" of the database.
  Here is the best strategy for your project:
  The "Migration/Owner" User (The Super User):
  Use your POSTGRES_USER (the admin user) when running drizzle-kit migrate or drizzle-kit push. This user has the power to create tables, change schemas, and grant permissions. Drizzle uses this user to manage the structure.
  The "Service" Users (The Limited Users):
  Use the restricted users (auth_user, game_user) in your docker-compose.yml for your actual backend services. Your running services use these users to perform daily tasks.

Industry Standard vs Overkill
  1. The "Secret/Config" Tier List
    | Data Item | Should it be in `.env`? | Should it be in `secrets`? | Why? |
    | --- | --- | --- | --- |
    | **Passwords** | **NEVER** | **YES** | If leaked, you lose control of the system. |
    | **Usernames** | **YES** | No | Used for config, but not dangerous if known. |
    | **Database Host/Port** | **YES** | No | Needed for services to find each other. |
    | **Schema Names** | **No** (Hardcode) | No | Changing these requires code changes anyway. |
    | **API Keys/Tokens** | **NEVER** | **YES** | High-value targets for attackers. |

  2. What else should be in `.env`?
    * **Service Ports:** If you ever need to change the port your `auth-service` runs on (e.g., `AUTH_PORT=3001`), you change it in `.env` and Docker Compose, not hardcoded in the app.
    * **Debug/Environment Flags:** `NODE_ENV=development` vs `production`. This changes how your app behaves (e.g., showing errors vs. hiding them).
    * **Database Pool Settings:** `DB_MAX_CONNECTIONS=20`. Sometimes you need to tune this for performance as your app grows.
    * **Feature Flags:** `ENABLE_NEW_GAME_MODE=false`. This lets you push code for new features without turning them on for users until you are ready.

  3. What you SHOULD NOT put in .env
    UI/Design Constants: Colors, fonts, or text labels => CSS/code.
    Internal Application Logic: => code for this
    Schema Names

  4. A Pro-Tip for your Monorepo
    monorepo (auth, game, website) => one huge .env => will become a "God File" and a nightmare to manage.
    Use a hierarchical approach:
      Root .env: Global things like POSTGRES_DB, POSTGRES_USER.
      backend-services/auth/.env: Service-specific things like AUTH_PORT.
      backend-services/game/.env: Service-specific things like MAX_PLAYERS_PER_ROOM.
      # packages/database/.env usually doesn't need its own .env file! 
        The database is a resource that the services consume. 
        Your database/ folder should just contain the SQL scripts, not its own configuration.

PWD stands for Print Working Directory.
  Docker Compose: It automatically knows what ${PWD} is. You don't need to define it; it is a built-in feature of Docker Compose.
  Makefile: It also knows what $(PWD) is.
  Crucial Rule: In a Makefile, use $(PWD). In docker-compose.yml, use ${PWD}.

Makefile: ${} vs $( )
  You are actually using a mix, and here is the distinction:
  $(VAR): This is the Makefile syntax for accessing variables defined inside the Makefile or passed in from the environment.
  ${VAR}: This is shell syntax. 
          When you put this inside a Makefile command (the lines starting with @), 
          the Makefile passes that string to the shell (sh or bash). 
          The shell then evaluates it.
  ${VAR} vs $(VAR): The Rule of Thumb
    The simplest rule is: Use $(VAR) for everything in a Makefile.
        $(VAR) (Makefile variable): The Makefile itself handles the replacement before it even talks to the shell.
        ${VAR} (Shell variable): The Makefile passes the string ${VAR} to the shell, and the shell tries to replace it.
    Example of why $(VAR) is better:
        ```
        Makefile
        include .env # This loads variables into Makefile memory

        all
            # Makefile replaces $(DB_VOLUME_NAME) with the value from .env
            # The shell only sees the final result, e.g., "big2_data"
            @mkdir -p /home/aimokhta/data/$(DB_VOLUME_NAME)
        ```
    Where you SHOULD use ${}
        Only use ${} inside your docker-compose.yml file. Docker Compose uses ${} syntax to look up environment variables from your .env file.

Why envsubst?
  The envsubst command is a standard Linux tool. 
  It reads a file, looks for things that look like shell variables (${...}), 
    replaces them with the values found in your environment, and outputs the result.
  By piping it (cat ... | envsubst | docker exec...), 
    you are safely injecting your environment secrets into the SQL command 
    without having to write them into your code files.

TSConfig: Use the simpler alias @big2/database/*.
Imports: Use import * as schema from '@big2/database/auth.schema';.
Makefile: Use envsubst to bridge the gap between your .env variables and the SQL script.

Cross-Package Usage:

  "dependencies": { "@big2/database": "workspace:*" } 
  (if using a monorepo manager like pnpm or yarn workspaces).

pg
  What it is: pg stands for "node-postgres".  
  Purpose: It is a collection of node.js modules for interfacing with your PostgreSQL database.  
  How it works: It acts as the low-level driver that handles the actual network connection, 
                sends SQL queries to your database, 
                and returns the results to your application.  
  Why you need it: Drizzle ORM (which you are using) is built on top of pg. 
                   Drizzle provides the developer-friendly syntax, 
                   but it relies on pg to perform the heavy lifting of talking to the database.  

@types/node
  What it is: This is a Type Definition package for Node.js.  
  Purpose: TypeScript, by default, does not know what Node.js-specific objects like process, fs (file system), or path are.  
  How it works: By installing @types/node, you provide TypeScript with the type information for all built-in Node.js APIs.  
  Why you need it: It allows your editor to provide autocomplete and type checking for Node.js features.  
                   Without it, your TypeScript files would throw "cannot find name" errors whenever you use standard Node.js global variables 
                   like process.env (which you use to access your database credentials) 
                   or functions like fs.readFileSync.
